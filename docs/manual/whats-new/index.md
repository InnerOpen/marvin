# What's new

Since 1.0.0-rc.39 (30 July 2026). This page covers releases rc.40 through rc.197 (4 October 2026). Version numbers name the `chore(release)` that first shipped each change; commit hashes are in [`CHANGELOG.md`](https://github.com/InnerOpen/marvin/blob/develop/CHANGELOG.md).

!!! note
    The last release cut in July was rc.39. rc.47 (4 September) only fixed an agent 500; the first feature after July is rc.40.

## Forms and submission protection

A submittable entry type is now a form: the public submit resolves the slug to the entry type, validates against its field schema and creates a `status=inbox` entry that emits `form_submission_received` (rc.42; the legacy Forms path stays as a fallback). The publishing `GET` serves the submittable schema (rc.44). Opt-in per-type rate limiting and CAPTCHA run before validation (rc.45). Platform-wide submission protection with per-workspace overrides adds review-not-reject mode, domain block/allow lists, disposable and personal-domain presets, exempt IPs, client capture and surge detection (rc.67). A submittable type can keep one entry per person: with **Same person = same …** (`matchField`, e.g. `email`) a repeat submission updates the submitter's entry (merging new values, counting `submission_count`, reopening an archived entry to the inbox) instead of creating a second one, the visitor sees the same response, a flagged repeat still lands as its own `needs_review` entry, and `form_submission_received` gains `duplicate`, `existing_entry_id` and `previous_status`. Details: [Forms and submission protection](forms-and-submission-protection.md).

## Workflows

The webhook step accepts `auth_scheme` (`Token` as well as `Bearer`, rc.50), resolves `{{SECRET}}` refs in configured headers (rc.53), fails on a non-2xx response (rc.54), takes a method on raw URLs and templates in stored URLs (rc.61), and returns the response `body` to later steps. `form_submission_received` can trigger a workflow (rc.51). The entry context carries `summary` and schema fields (rc.52). The entry step gained `set_metadata`, metadata targeting for external ids (rc.59) and `entity_query` (rc.60). A **Set fields** step (`set_data`) writes an entry's schema fields, a **Run integration** step runs a provider action and keeps its result, entry metadata joins the context and template paths take list indexes (rc.111). `${entry.image}` gives the featured image URL (rc.119). "Run on a query of entries" gives each row the full entry, so `entry.data.*` conditions work, and the query gained a **Fields equal** filter (rc.129). Typed values in Set fields and conditions convert to the field's type (rc.131). Workflow targets, `entity_query`, the agent's `find_entries` and bulk agent actions now share one entry query with `where` operators, date filters and sorting (rc.138); an unknown `where` operator matches nothing instead of being ignored, and runs started by the agent's `run_workflow` are recorded under **Runs** (rc.139). **Emit event** can emit `site_build_*` and `site_deployment_*` events with a message, failure reason and site URL, so a host's deploy notification becomes a Marvin event (rc.144); those events can be subscribed to for notifications (rc.151) and trigger other workflows from a new **Site** trigger group (rc.152). A **Run integration** step resolves `{{SECRET}}` references in its args (rc.145), and AI-operation steps respect the workspace's AI limits and token cap (rc.146). A run announces itself with `automation_started`, so its toast shows it running and then turns into the result (rc.165). **Dry run** of an event-triggered workflow uses a sample event from the log, or an entry, and shows whether the trigger fires, a ✓/✗ line per condition and the resolved steps (rc.173). An entry step whose publish is refused fails with the reason (rc.175). `${site.url}` is the workspace's Canonical URL (rc.177). Every event names its subject, a run names what triggered it, and `automation_ran` lists each step and its outcome (rc.178). An entry step that finds its target by query can skip quietly when nothing matches (`if_none: skip`), and `${entry.url}` is an entry's page on the site (rc.179). **On-failure steps** run when a step fails, a `request_review` entry op sends the entry to Needs review with a reason, and a provider's error code reaches them as `${error.code}` (rc.193). Integrations' error policies apply to workflow steps (rc.197; see the box below). Details: [Workflows](workflows.md).

!!! warning "Behaviour changes in the integration error handling release (rc.197)"
    - **A workflow no longer cascades into itself.** A workflow never reacts to an event its own run caused — its entry step's `entry_updated`, its own `automation_ran` — or one a reaction to its run caused. Before, it re-ran until the reaction-depth limit (3) stopped it. Other workflows still react, and later, independent events trigger it as usual.
    - **`${error.code}` is `unknown`, not empty,** for a provider error that names no code.
    - **The Run integration step catches every exception** from the provider, not just `ValueError`, so a provider bug fails the step (and its on-failure steps and error policy run) instead of escaping the run.
    - **`automation_failed` carries `handled`** (the integration's error policy took the failure in hand; toasts are yellow), `handling` (what it did) and, on a retry run, **`retry_attempt`**. A retry chain announces its first failure and its end, not each retry in between.

## Incoming webhooks

An incoming webhook can name a workspace secret (`signing_secret_ref`) and a header (`signature_header`, default `X-Signature-256`); requests must then carry `sha256=<hex HMAC-SHA256 of the raw body>` or get 401 (rc.55). The admin card edits signing and can generate a key stored as a secret and shown once (rc.56). Rejected signatures log their shape (rc.57) and accepted payloads log their key structure, keys only (rc.58). Signature schemes followed: core presets, presets contributed by integrations and a custom scheme (rc.111, rc.113). A `static_token` scheme, and token mode for integration and custom schemes, accept senders that send a fixed shared secret in a header instead of signing (rc.144). Details: [Incoming webhooks](incoming-webhooks.md).

## Outgoing webhooks

A new `workflow` webhook type never fires from the event bus; only a workflow's "Call webhook" step calls it, and those calls now write delivery-log rows (rc.63). Details: [Outgoing webhooks](outgoing-webhooks.md).

## Agents and Ask

Workspace agents are definable persona or model agents with a run endpoint and MCP tools (rc.70). A per-tool permission matrix, an Agents settings page and Ask as the agent chat followed (rc.71), then a read-only `view_image` tool with sticky attachments (rc.72), a `workspace_overview` tool (rc.73) and a preamble that lists connected MCP servers (rc.74). Ask threads are stored server-side (rc.76) and live run steps can be polled while a run is in flight (rc.77). The built-in `marvin` agent became a router that hands off to and refers users to other agents (rc.98–rc.100), and the `ask` tool policy became **Ask first**: the run pauses on its thread until the user approves (rc.107). Agents got a workspace inventory and a forgiving workflow lookup (rc.108); unpriced models show an unknown cost instead of "Free" (rc.110). A blank persona means Marvin's default voice (rc.133). Approval mode now covers every AI write-back, the bubble and Ask send the `agent` invocation source, and the unused forms/actions/scheduled source toggles are gone (rc.134). The bubble uses the workspace's assistant name and icon (rc.135), and `find_entries` can filter on an entry type's own fields (rc.136). The main agent is listed under the assistant name everywhere (rc.140). **Reindex now** runs in the background, batched and incremental, with status on the Ask page (rc.141), and the search index holds published entries only (rc.142). AI Settings gained a **Usage & Limits** card with a monthly cost limit and budget toasts; agents answer about a connected MCP source themselves and say when they cannot reach one; executions name agent runs `agent:<name>` (rc.146). The official OpenAI API moved to the Responses API, a refused parameter is learned per model, and no temperature is sent unless `AI_DEFAULT_TEMPERATURE` is set (rc.147–rc.149). Bubble conversations live in server threads, survive navigating away mid-run and appear on the Ask page (rc.150). The bubble can show an animated character instead of its icon, one GIF, WebP or PNG animation per state, uploaded under AI Settings → **Persona → Bubble character** (rc.153). Platform admins keep a **Character Library** that any workspace or agent can pick from, custom agents get characters of their own that the bubble shows after `/use` and while a hand-off works, and the bubble keeps its threads per workspace, so a tab that switches workspaces no longer sends the other workspace's thread (rc.156). The character picker became a row of cards (rc.157). Uploads clear an image's solid background, and a library pack in use can be deleted after a confirmation that moves its users back to their icon (rc.159). An agent's character moved into its **Edit** form, under Icon and Name (rc.160), with the card's **Character** button kept (rc.161). A bulk tag or image write of more than 20 links, or of more than 5 items across several targets, asks first whatever the policy, `generate-tags` looks at the image, and runs a restart killed are marked failed with a note on their thread (rc.162). The Ask page's **Threads** panel lists every agent's threads, bubble conversations included, with hand-offs nested under their parent (rc.163). Agents can search and read this manual with `search_docs` and `read_doc` (rc.166). Entry tools return each entry's site `url` once an entry type has a page URL pattern, and agents are told never to write placeholder links (rc.172). The bubble rests bottom-left and stays on screen (rc.174). Marvin's default voice is the full character, and a workspace with its own voice gets bubble lines written in it, editable under **Persona → Bubble lines** (rc.180). The bubble and the Ask page have separate invocation-source toggles (rc.185; rc.184 first hid the bubble when the old single toggle was off). The bubble's Marvin is bound through Marvin's own permission matrix, so its Ask-first tools pause there too (rc.187). Workspaces can define their own [tones](agents-and-ask.md#tones), pick the default and switch per conversation with the bubble's `/tone` (rc.188). A specialist's Ask-first call is carried up to `marvin` and approved from the Ask page, the bubble or a toast; agent drafts use the run's tone (rc.190). The persona is labelled **Character**, and where it and the tone disagree the tone wins on delivery (rc.192). **Preview** shows the prompt a tone, the Character or an agent sends, and an entry type's **Voice** field overrides the tone for its drafts (rc.194); the New agent form previews too, and the New entry type page has the Voice field (rc.195). Asked to delete entries, agents archive them with `archive_entries`, Marvin's reversible delete; a published entry asks first, and there is still no AI hard delete (unreleased; see [Archiving entries](agents-and-ask.md#what-it-does)). Details: [Agents and Ask](agents-and-ask.md).

## Marvin as an MCP server

External MCP tools are placed by their own `readOnlyHint` / `destructiveHint` into `mcp_read`, `mcp` and `mcp_destructive` rows of the matrix, and discovered tools appear in the catalog and permissions endpoints (rc.75). Ask-first tools are not offered to MCP callers, which have no thread to pause on (rc.107). MCP clients get `marvin_search_docs` and `marvin_read_doc` for this manual (rc.166). A new registry tool, `describe_event`, answers "what happens when X?" for the agent and MCP clients from the Events pages' own lookup: what sends an event, what reacts to it and when it last happened (workspace OWNER/ADMIN; a hint such as `publish` finds the event). A direct MCP tool call follows Marvin's permission matrix like an agent run: a blocked tool is refused and no longer listed, and an Ask-first one — running a workflow — is refused with a pointer to the Ask page, since a direct call cannot pause for approval (unreleased). Details: [Marvin as an MCP server](marvin-as-mcp-server.md).

## Scheduled tasks

`run_integration_action` calls one provider action for one integration on a schedule, feeding entries in and persisting returned records as entries (rc.78). A handler may return `None` for a routine no-op and the automatic run is not logged; manual runs always are (rc.96). `prune_scheduled_task_executions` ships as a system task with 30-day retention (rc.97). The entry editor saves Scheduled Publish and Expiration Date in the viewer's time zone, **Published** became read-only, and a scheduled publish runs once and leaves archived entries alone (rc.168). `publish_scheduled_entries` and `unpublish_expired_entries` ship as 5-minute system tasks, so scheduling works with no setup, and publishing by any route clears the schedule (rc.170). Scheduled publish and expiry fire the same entry events as a manual change, so smart collections, workflows and rebuilds react (rc.171). Expiry clears the expiration date, and publishing with a passed one is refused (rc.175). A held-back scheduled publish records why on the entry, shows it in the editor and as a **Scheduled publish waiting** toast once per reason, and **Scheduled publish only for approved entries** can make it wait for approval; a refused save keeps your edits and says why (rc.176). A routine run with nothing to report emits no `scheduled_task_completed` (rc.178). Details: [Scheduled tasks](scheduled-tasks.md).

An action input can name the read action that lists its valid values (`x-marvin-options`): **Run action** and the workflow **Run integration** step show a searchable list loaded through the connection, with free text as the fallback (rc.197). Providers can ship their official logo (SDK 0.6.0); Marvin validates it and shows it on the integration cards, the catalog, **Admin → Plugins** and workflow steps, falling back to the emoji (rc.197). The integration routes and Settings → Integrations became workspace-admin only, as did running an action, a health check or an option list (rc.197). An n8n provider package triggers n8n workflows from a workflow step (picked from n8n's own list, signed with a short-lived JWT), reads a run's status back and records n8n's results on the entry through an incoming webhook (see [n8n](n8n.md)). A new **Alerts & health** page (Settings → Integrations) shows each connection's last successful action and last check, open alerts with Test and Resolve, retries waiting with **Retry now** and **Give up**, the last 7 days of failures an error policy handled, and resolved alerts with how long they were open; the **Integration alerts** routing card moved there (see [Alerts & health](integrations.md#alerts-health)). The **Installed plugins** list moved from the Integrations page to the bottom of **Alerts & health** (linked as **Alerts, health & plugins**). Details: [Integrations](integrations.md).

## Blueprints

A blueprint declares a collection, entry type, scheduled task or event subscription without creating it; applying creates only what is missing and never overwrites (rc.84). A workspace API browses and applies them (rc.85), parameters and a content-neutral core catalog followed (rc.86). Integrations can declare `entry_fields`, `incoming_webhook` and `workflow` blueprints, and applying needs ADMIN or OWNER (rc.111). Parameters are picked from dropdowns (rc.116), an integration parameter defaults to the workspace's own connection (rc.117), and an applied workflow can be updated to its integration's current version (rc.118). The connected-integration card is where blueprints are applied. Details: [Blueprints](blueprints.md).

## Publishing API

`PublishedEntryListItem` carries `data` and `description`, so a site renders a collection from one request (rc.48). Entries of non-publishable types are never served (rc.62). Site rebuild requests are coalesced per workspace (rc.121), with the wait windows as settings (rc.122). Published content changes queue a rebuild on their own, behind **Rebuild the site automatically** in Settings → General (rc.143), and a host's build and deploy notifications can come back as Marvin events and toasts (rc.144). A rebuild records the changes it covers: `webhook_triggered` carries `requestCount` and `changes`, and the **Site rebuild** toast lists them under "N changes ▾" (rc.154); the event catalog describes those variables (rc.155). A queued rebuild is announced once with `site_rebuild_queued` and its toast (rc.165). An entry type can have a **Page URL pattern** that, with the workspace's Canonical URL, gives each entry a `url` in the publishing API and a **View on site** button, and placeholder links such as `[title](#)` block publishing (rc.172). API clients can be edited, the client form offers the **Forms** permissions a submitting site needs, and only a disabled client can be deleted (rc.181). A private collection can't be read through the entries `collection` filter (rc.186). Changes no site can see (entries of non-publishable types, private collections) no longer queue a rebuild (rc.191). **View on site** stays disabled until the entry is published (rc.194). `POST /api/platform/site/rebuild` (EDITOR and above) queues a rebuild through the same coalescing queue and says what will build the site, or answers 409 when nothing would; `GET` on the same path shows the queued rebuild, the last one sent and the newest build or deploy status. `?expand=full` on a collection, the entries list or a resource's entries returns every entry in the single-read shape (`assets[]`, `resources[]`), so a site no longer reads each entry again. Details: [Publishing API](publishing-api.md).

## Media embeds

Paste a YouTube, Vimeo, Spotify, SoundCloud, Apple Music, Apple Podcasts, TIDAL, Simplecast or Transistor link, or Bandcamp's embed code, and the site shows a player. A supported link alone on its own line in a markdown field becomes a player; turn that off per field with **Auto-embed media links** (`autoEmbed: false`). A new **Media embed** field type holds one player. The markdown editor has an **Embed** dialog, and its preview now renders sanitised markdown (marked + DOMPurify) with the players in place. The publishing API carries `embeds` on every entry and list item, keyed by the link as written, and `site.embeds` holds the privacy mode, consent text and player origins. **Embeds & Privacy** in the site settings chooses between click-to-load (the default; nothing third-party loads before a click) and direct players. Marvin builds every player itself from an allow-list and resolves titles through a platform-wide cache, so publishing never calls a provider. The agent tools are `add_embed`, which stages a suggestion, and `preview_embed`. Migration `a78a8895a6a1`. Details: [Media embeds](media-embeds.md).

## Event Log

A workspace admin chooses what the Event Log records. **Audit coverage** on the Event Log has a switch per event type, grouped by category, with a filter box and **Reset to default**. Other members see the list of types left out, which used to be a fixed list on the page. Security events (members and invitations, API clients and tokens, secrets, workspace settings and AI approvals) are always recorded, and so is each change to these settings (`workspace_settings_changed`). The routes are `GET`/`PATCH /api/groups/audit-settings` (OWNER/ADMIN) and `GET /api/groups/audit-settings/excluded` (any member). Migration `e6c2a9f4b1d3`. Details: [the manual's Event log section](../index.md).

Platform events left the workspace Event Log for a new super-admin page, **Admin → Operations → Events** (`/admin/events`). Sign-ups and other account events, workspaces created, edited or deleted by a platform admin, a user switching workspace, token refreshes, personal API tokens and the platform's security and backup events used to show up in the log of whichever workspace they were recorded with. They are still stored and still fire the same webhooks and workflows, but the Event Log, activity toasts, the dashboard, workflow dry-run samples and the agent's event tools leave them out, and the audit coverage panel no longer lists them (they are always recorded). The admin page lists them across workspaces with the workspace and user, filters by type, workspace and date, and pages through them; the Overview has a card for them. New routes: `GET /api/admin/events`, `GET /api/admin/events/{event_id}` and `GET /api/admin/events/catalog` (super admin). Details: [the manual's Platform events paragraph](../index.md).

## Events

Each event type now shows its whole story on **Automation → Events → <event>**: **Sent by** (Marvin's own code, workflows, the incoming webhooks that start them, scheduled tasks), **What happens** (every workflow, integration action, email and webhook on it, switched-off ones too, then Marvin's built-in reactions) and **Recent** (its newest Event Log rows, or a note when Audit coverage leaves it out), with **Caused by** / **Leads to** links along its chain. Connections made elsewhere, such as workflows and anything an integration installed, are listed read-only with their On/Off state, an **Installed by** badge and a link to where they are managed. The **Subscribe** menu gained **+ New workflow on this event**, which opens the workflow builder with the trigger filled in. The Events list counts every kind of connection with one request, so integrations' workflows no longer look disconnected; the Workflows page marks what an integration installed; and **Admin → Events** shows the same view for a platform event when filtered by its type. Platform events (sign-ups, workspaces, platform tokens, security, backups) left the workspace side: `GET /api/event/types` no longer lists them, so the Events list and the webhook, email and integration pickers don't offer them (Marvin's own welcome and password-reset emails still send, and a workspace template of type welcome, password reset or invitation replaces one with the **Replaces Marvin's … email** switch on its page, which lists that email's variables). Details: [the manual's Events paragraph](../index.md).

The catalog was tidied. `webhook_triggered` is now called **Site Rebuild Sent** and sits under Publishing: it is the signal deploy hooks listen to (the internal name is unchanged, so existing webhooks keep working). Events that were listed but never sent are now sent or hidden: **Webhook Created**, **Updated** and **Deleted** come from the outgoing-webhook routes and **Webhook Delivery Failed** from a delivery that failed after its retries (none of them carries the webhook's URL or headers), and **API Token Created**, **Rotated** and **Revoked** from your personal tokens (platform events, always recorded, never the token). `webhook_delivery_succeeded`, `site_published` and the three security signals with no feature behind them are hidden from every list and picker until something sends them. `site_build_*` became old names for `site_deployment_*`: a workflow trigger, Emit event step or subscription that names one is saved as its counterpart, and migration `011f6c720d1d` rewrote any already stored. Details: [the manual's Events paragraph](../index.md).

## Auth and tokens

No new token type this period. Secrets are now resolved in webhook headers (rc.53), incoming-webhook signing keys are stored as workspace secrets (rc.55, rc.56), CAPTCHA secrets come from the workspace store via `{{SLUG}}` refs (rc.45) and integration action arguments can reference secrets (rc.145). API client routes, reads included, became workspace OWNER/ADMIN only, as did creating, changing and deleting secrets (rc.182); revealing a secret checks the workspace role, and new personal and API client tokens are shown once in a dialog instead of in the page URL (rc.183). Workspace settings became workspace OWNER/ADMIN only, reads included: integrations, outgoing webhooks, scheduled tasks, SMTP, variables, email event subscriptions, test email, export and backups, and the invitation list. Content routes now enforce the workspace roles: VIEWER reads only, AUTHOR creates entries and edits their own until approved or published, EDITOR manages all content, and ADMIN changes entry types and forms; the admin hides controls a role can't use. AI and MCP write tools need EDITOR, and the scheduled-task, workflow and AI-settings tools need ADMIN (rc.197). See [Auth and tokens](../auth-and-tokens.md).

# Agents and Ask

Named agents with a per-tool permission matrix, plus an Ask page that keeps conversations, citations and live tool steps on the server.

## What it does

Three built-in agents exist in every workspace (they are code, not rows, so nothing is seeded):

| Slug | Kind | Tools | Notes |
|---|---|---|---|
| `marvin` | persona | every tool your role allows | the default agent and the router: it can hand a question to another agent; in-workspace writes are allowed, workflow runs and external MCP writes ask first. Listed under the workspace's **Assistant name** |
| `ask` | persona | `search_content`, `workspace_overview`, `search_docs`, `read_doc`, `suggest_agent` | grounded answers only; cites the entries it used; can refer you to another agent but never runs one |
| `chat` | model | none | plain conversation; tells you to use Ask or Marvin for content questions |

The `marvin` agent carries the workspace's assistant name (AI Settings → **Persona**), so after a rename the Ask page's agent picker, the bubble's `/agents` list, MCP `list_agents`, hand-offs and the `chat` agent's "use the … agent" pointer all use the new name; the slug stays `marvin`.

Admins can define more on the **Agents** page. An agent is a definition with these fields: `kind` (`persona` = instructions + tools, run through the tool loop; `model` = a plain completion, no tools), `system_prompt`, `model_override`, `tool_allowlist` (hard filter; `null` = no restriction), `min_role` (who may talk to it, 1–5), `sources`, `enabled`, `allow_writes`, `tool_policy`, `icon`, `suggestions` (up to 8 suggested prompts), `default_register` (a tone slug: `auto`, `professional`, `playful` or one of the workspace's own [tones](#tones); an unknown slug is a 422) and `handoff_hint` (one line telling the router when to hand a question to this agent). Slugs may not shadow the built-ins.

Every persona run gets a workspace preamble that says which workspace it is in, that "the RAG / knowledge base / index" means the workspace content, which bound tool answers which kind of question, and which external MCP servers are connected. A reply that only promises to check something ("give me a moment") is nudged once to act instead. When you name a connected MCP server ("check the vault"), the agent answers from that server's tools itself and does not hand the question to another agent unless you name that agent, since the others may not see the server. An agent with no external MCP tools bound says it cannot reach an outside source rather than presenting workspace results as coming from it.

**Hand-offs and referrals.** `marvin` sees a roster of the other agents you may talk to (their description and "Hand off when…" line). When you name an agent, ask for its voice, or the question matches its hint, `marvin` calls `run_agent`, then answers in its own voice and names the agent it asked. The specialist runs with its own matrix on a child thread and cannot hand off further (`AI_HANDOFF_MAX_DEPTH`, default 1, allows deeper chains; an agent already in the chain is never handed to again). Other agents cannot hand off (the `agents_run` row defaults to Block except on `marvin`); they can call `suggest_agent`, which records a referral the answer shows you. Executions started inside an agent run carry `parent_execution_id` in their metadata.

**Permission matrix.** Every bindable tool belongs to one category (`entries_read`, `entries_author`, `entries_archive`, `entries_trash`, `links`, `library_read`, `assets_import`, `automation_read`, `automation_run`, `automation_author`, `insights`, `docs_read`, `agents_read`, `agents_run`, `ai_ops`, `mcp_read`, `mcp`, `mcp_destructive`, `other_read`, `other_write`). `tool_policy` maps a category id or tool name to `allow`, `ask` or `block` (shown as Allow, Ask first, Block). Resolution order for one tool: allowlist, then a tool-level entry, then a category-level entry, then the category default:

- reads allow;
- `agents_run` (hand-offs) allows only on `marvin`;
- writes on a workspace agent ask first when **Allow writes** is on and are blocked when it is off;
- on `marvin`, writes allow except `automation_run`, `mcp` and `mcp_destructive`, which ask first.

A write is never bound for a caller below EDITOR, whatever the matrix says, and that holds for `ask` too: agent writes can reach any entry, and an AUTHOR may change only their own drafts.

**A built-in agent's matrix.** Workspace admins and owners can change the matrix of the persona built-ins, `marvin` and `ask`, for their workspace: **Edit permissions** on the agent's card under **Built-in agents**. Nothing else about a built-in can change (its name, instructions, model, allowlist and the rest stay as defined in code), and `chat` has no tools, so no matrix. The editor starts every row at the built-in's own default (on `marvin`: reads and in-workspace writes allow, workflow runs and external MCP writes ask first, hand-offs allow); `ask`'s editor lists only its five tools, since Allow cannot reach past an allowlist. The card says **permissions: Default** or **permissions: Changed**, and **Reset to default** drops every change. The change applies everywhere the agent runs: the bubble, the Ask page, hand-offs to it, MCP `run_agent`, and, for `marvin`, direct MCP tool calls and the MCP tool list. It never lifts a floor: writes still need EDITOR, big bulk writes still ask first, and archiving a published entry still asks first under Allow. Workspace export and import carry the changes (`agentToolPolicies` in the AI settings). Like other agent edits, a change is not recorded in the Event Log.

**Ask first.** An `ask` tool is bound, but when the model calls it the run parks on its Ask thread (status `awaiting_approval`) and the page shows a card with one checkbox per pending call: **Approve selected** or **Deny all**. Approved calls run, denied ones tell the model you declined, and the run continues on the same thread and execution (`POST /api/ai/threads/{id}/resume`; a missing decision counts as a deny, and only the thread's owner may decide). Where there is no thread to park on — an MCP `run_agent` call, the bubble's `/agent` without a thread, a hand-off under such a run — an `ask` tool is not bound, so it behaves like Block. A direct tool call from an MCP client (`POST /api/ai/tools/{name}/invoke`, what MarvinMCP's `marvin_<tool>` tools use) stands in for `marvin` and resolves each call through `marvin`'s matrix the same way: Allow runs (still behind the role floor and the bulk-write and ask-first refusals), while Block and Ask first are refused with a message naming the category, and nothing runs — so `run_workflow` runs only where you can approve it. An Ask-first refusal also says where to change that: set the row to Allow for Marvin under Settings → AI → Agents (see **A built-in agent's matrix** below). Decisions emit `approval_granted` / `approval_rejected` events, and a park emits `approval_requested`, which pops up an activity toast for you (only you, the thread's owner) linking to the conversation — or, with the Ask page switched off, opening it in the bubble.

**A specialist's ask.** When `marvin` hands off and the specialist reaches an Ask-first call, the specialist parks on its own child thread and `marvin` parks with it, so the approval shows up in your conversation with `marvin` (Ask page or bubble). The card lists `marvin`'s own pending calls first, then each specialist's, each with a **via Workshop** chip; their ids are paths such as `c1/c7` (the hand-off call, then the specialist's call). One decision settles all of them: the specialist resumes first on its own thread and execution, its answer becomes the hand-off's result, and `marvin` finishes with one answer. If the specialist asks again, `marvin` parks again without running, and a new card shows the new ask. Two specialists can wait side by side; asking the same specialist twice while its first request waits gets an error instead of dropping that request. Deciding on the specialist's own thread (reached through "Handed off: X ↗") passes the decision up to `marvin`'s conversation, and the answer lands there; when `marvin` is also waiting on other actions, deciding there is refused (409) so nothing you have not seen is denied — decide on `marvin`'s conversation. Permissions are checked again when you decide, never widened: you must own every thread involved and still be allowed to talk to each agent and `marvin` must still be allowed to hand off (otherwise the specialist's request ends as no longer permitted and `marvin` is told so), and each run's tools are bound again at your current role, so an approved action that is no longer allowed is not run. A new message on either thread ends both pending runs ("I stopped here…"). Each execution keeps an append-only record of the decisions on it (`metadata_json.approvals`: when, who, from which surface, why, each call's decision). The approval events fire once, on `marvin`'s thread, and carry `via_agent`, `child_thread_id`, `child_execution_id`, `decided_by`, `surface` and, for a run ended without your decision, `reason` (`abandoned`, `expired` or `no_longer_permitted`). A specialist that cannot be resumed at all (no model configured since, say) has its request ended with reason `failed` in its record, and `marvin` answers without it.

**Expiry.** A run waiting for approval expires after `AI_PARKED_RUN_TTL_HOURS` (default 168, seven days; `0` never). An hourly task ends expired runs, specialists' included: the pending calls are denied, the executions fail "expired", the thread gets a short "This request expired before it was approved" reply, and `approval_rejected` fires with reason `expired`. There is no notification yet. Approving an expired run gets a 409 and ends it the same way.

**Big bulk writes ask first.** `attach_tag`, `detach_tag` and `import_asset` with `attach_to` size each call before running it: targets × items is the number of links it would make. A call of more than 20 links, or of more than 5 tags (or images) across more than one target, pends as an Ask-first call even where the matrix allows the tool outright and whatever the approval mode. The approval card shows a summary such as "Attach 12 tags to 19 assets (228 links)" and lists the targets and items. Where the run cannot park (no thread, an MCP `run_agent` call, a hand-off under a run without a thread, a direct MCP call to the tool), the tool writes nothing and answers with the summary and counts, telling the caller to work in smaller steps or to run it from the Ask page or an agent conversation, where you can approve it.

**Deleting entries, assets and resources: the Trash.** `trash_entries(entries, assets?, resources?, reason?)` is what Delete does in Marvin: asked to delete, remove or clear out entries, an agent moves them to the [Trash](trash.md), where you can restore them. It works exactly like `archive_entries` below — up to 50 entries per call by slug or id, the entry page's permission check per entry, a published entry asks first (the approval card says "Move N entries to the Trash — K are published and will come off the site"), and nothing is written where the run can't park — but sets the status to `trashed`, so `entry_updated`, `entry_unpublished` (for a published entry) and `entry_trashed` fire. The answer says the entries are in the Trash, how to restore them, and carries a `trashLink` to the Trash for the agent to pass on. It has its own `entries_trash` row in the matrix, with the same defaults as `entries_archive` (Allow on `marvin`, Ask first on a workspace agent with **Allow writes**, never for an AUTHOR). `restore_entries(entries, assets?, resources?)` is the Trash's Restore, in the same matrix row: asked to restore, undelete or bring back entries, an agent takes them out of the Trash, each back to the status it had (a published entry comes back as a draft, so a restore never puts anything on the site); entries not in the Trash are reported, not changed. Both tools also take `assets` (by id, slug, or filename or name when only one asset has it) and `resources` (by id, slug, or name when only one has it), up to 50 items per call in all; a name two items share is skipped, never guessed. Assets and resources move as their pages' **Move to Trash** and **Restore** move them (`asset_trashed`, `resource_restored`, …; an asset's file is kept), and the answer lists them under `trashedAssets` / `trashedResources` (or `restoredAssets` / `restoredResources`). Trashing an asset or resource a site shows (attached to a published entry, in a collection visible to sites, or the site logo) asks first like a published entry: "Move N items to the Trash — K are on the site and will come off it". A call that names only entries answers exactly as before. No tool empties the Trash or deletes forever: that stays a person's action. The preamble tells an agent with `trash_entries` to use it for deleting entries, assets and resources (never detaching an asset to "delete" it), `restore_entries` for bringing them back, and `archive_entries` for retiring; an agent with only `archive_entries` archives instead.

**All of them: `match`.** "Delete all the assets" or "trash every unattached image" doesn't fit a list of 50 names, and a model once passed `assets: ["*"]`. `trash_entries` and `restore_entries` also take `match: {kind, all?, query?}`. `kind` is `entries`, `assets` or `resources`, one per call. `all: true` means every one of that kind in the workspace: not trashed for `trash_entries`, in the Trash for `restore_entries`. `query` selects some, in the vocabulary the kind's lists already speak. For entries that's the shared entry query `find_entries` and workflows use (statuses can't be used when restoring, since everything there is `trashed`). For assets and resources it's the shared asset/resource query that `list_assets`, `list_resources` and `attach_tag`'s `filter` use: `asset_type(s)`, `mime_type(s)`, `resource_type(s)`, `query` (name, slug or filename), `tags`, `collection`, `unattached` (on no entry; a link to a trashed entry still counts) and `created_after` / `created_before`. A match needs `all: true` or a non-empty `query`, not both. A key the kind doesn't understand, or a tag or collection that doesn't exist, selects nothing and says why; it is never dropped. Names and a match can be combined, and an item named and matched counts once. A call with a match always asks first, whatever the matrix says. The card reads, for example, "Move 137 assets to the Trash (every asset in this workspace). They can be restored from the Trash; nothing is deleted forever", adds how many are on the site, and lists a sample of names. Where the run can't park, nothing moves and the answer gives the count. One call moves at most 500 matches. The answer's `matched` gives `total`, `selected` and `remaining`, and when some remain it tells the agent to call again with the same match, which asks again. Permission checks and skips work per item as for named ones. A wildcard in a list of names (`*`, `all`, `everything`, `all assets`, …) that names nothing real is an error pointing at `match`. A call without `match` answers exactly as before.

**Archiving entries.** `archive_entries(entries, reason?)` retires entries that should be kept: asked to archive or retire entries (or, without `trash_entries`, to delete them), an agent archives them. It takes up to 50 entries per call, by slug or id. It changes the status the same way as choosing Archived on the entry page, so `entry_updated`, `entry_unpublished` (for a published entry) and `entry_archived` fire, smart collections update, the site rebuilds and the event log records who did it. It needs EDITOR, like every AI write tool, and each entry is also checked as the entry page checks it. Entries the caller may not change are skipped and listed with the reason, and entries already archived are listed as such. Archiving a published entry takes it off the site, so a call that includes one asks first, whatever the matrix says: the approval card lists the entries with the published ones marked, and nothing is archived until you approve. Deny and nothing changes. Inbox, draft and review entries archive straight away. Where the run cannot park (no thread, a hand-off under such a run, a direct MCP call), a call with a published entry writes nothing and tells the model to leave the published ones out. The answer says how to undo it: archived entries are in the **Archive** collection (or Entries filtered by Archived), setting the status back restores one, and a once-published entry has to be published again. The tool has its own `entries_archive` row: Allow on `marvin`, Ask first on a workspace agent with **Allow writes**. There is no AI hard delete; deleting forever stays a person's action. `revise_entry` says it is not for deleting, and the preamble tells agents to trash (or, without the Trash, archive) instead of staging a revision, or, with neither tool, to say they cannot remove entries.

**Creating workflows.** Asked to create, build or set up a workflow or automation, an agent makes it rather than saying it can't. `workflow_authoring_guide(section?)` returns how a workflow is written, generated from the code that runs one: the definition's shape, the trigger types, the events a workflow can start on (grouped, with descriptions in detail), the target query keys (the same entry query as `find_entries`), condition operators and fields, each step kind with its required and optional fields, the entry ops and what each sends (`unpublish` and `restore` set an entry to draft), the template syntax (`${event.*}`, `${entry.*}`, `${steps.<id>.output.*}`, `${site.url}`, `${error.*}` in on-failure steps), and this workspace's collections, entry types and their fields, integrations and the actions a workflow can run, outgoing webhooks (id and name, never the URL), incoming webhooks, other workflows, AI operations and allowed jobs. Without `section` every part comes in brief (lists capped at 50); `section` (`shape`, `triggers`, `events`, `target`, `conditions`, `actions`, `templates`, `workspace`, `examples`) gives one part in detail. `get_workflow(workflow)` returns one workflow's definition, whether it is enabled and its last run, to copy or adapt; `list_workflows` lists them. `draft_workflow(name, definition)` saves a workflow switched off, through the same save as `POST /api/automations` (`enabled` in what it is given is ignored, and a whole `{name, definition}` document is accepted like the editor's JSON view). A definition the editor would refuse, an unknown key, or a name the workspace doesn't have comes back as `{error, issues: [{path, message}]}` with nothing saved, and the agent fixes it and tries again (at most three times, then it tells you what is still wrong). On success the answer has `editLink`, a finished link that opens the workflow in the editor, and any advisory warnings; the agent tells you it is switched off and what to check before enabling it. `update_workflow_draft(workflow, name?, definition?)` revises a workflow only while it is switched off: an enabled one is refused, so switch it off first or edit it yourself. The four tools need workspace ADMIN or OWNER, like the workflow routes. The guide and `get_workflow` are in **Automation: read**; `draft_workflow` and `update_workflow_draft` have their own row, **Automation: author** (`automation_author`): Allow on `marvin`, Ask first on a workspace agent with **Allow writes**, never for a role below ADMIN. The preamble tells an agent with `draft_workflow` to use it this way; an agent with only the guide writes the definition for you to paste into **New workflow → Edit as JSON**.

**Tagging.** Agents are told to choose tags per item from what that item is, never to attach a whole tag vocabulary wholesale, and to tag images with `generate-tags` one asset at a time. `generate-tags` describes the asset or resource it is given and, for an image asset on a vision-capable model, sends the image itself; its optional `vocabulary` input lists existing tags to reuse where they fit.

**Interrupted runs.** An agent run is one request, so a restart that kills the process mid-run (a deploy past its grace period, an out-of-memory kill, a crash) used to leave its execution `running` forever. When the server starts, executions still `running` from an earlier process are marked `failed` with "Interrupted: the server restarted while this run was in progress.", and the run's thread gets a short reply saying it was interrupted and that anything changed before the restart is kept, which the bubble picks up as the answer. Runs parked on an Ask-first approval are not touched; they resume on any process, until they expire (see **Expiry** above). Deploys first let runs finish (see [Operations → Helm chart](../operations.md#helm-chart)).

**Approval mode is a different thing.** The matrix decides what an agent may *do* (tag, attach, run a workflow). The workspace **Approval Mode** (see [Settings](#settings)) decides whether AI-*generated content* lands on a record without a person: it covers every AI write-back — an operation's write-back, revise, a workflow operation step with `write_back`, and the alt text compose writes onto assets. Held-back output waits as a suggestion to accept.

**Finding entries.** `find_entries` uses the same entry query as a workflow's "Run on a query" of entries, an entry step's `entity_query`, and the bulk `filter` of `attach_tag` / `detach_tag` (up to 1,000 targets), so a filter works the same everywhere. All keys are optional:

| Key | Meaning |
|---|---|
| `entry_type` / `entry_types` | type slug(s) |
| `status` / `statuses` | the **publish** status (`inbox` … `archived`, `trashed`; trashed entries are left out unless asked for); a value that is not one (usually a field's value) returns a note instead of a silent 0 |
| `fields`, `metadata` | exact match on the type's own fields or on metadata, `{field_key: value}`; typed-in text such as `true` or `12` matches checkbox and number values |
| `where` | `[{field, op, value}]`; `field` is a field key or `metadata.<key>`; `op` is `eq`, `neq`, `in`, `contains`, `exists`, `missing`, `gt`, `gte`, `lt`, `lte`. Comparisons read number-like text, so `"$1,170"` compares as 1170 |
| `query` | title or slug contains |
| `tags`, `collection` / `collections` | any of these (slug or name) |
| `has_images`, `has_assets`, `has_resources` | attachment filters |
| `created_`, `updated_`, `published_` + `after` / `before` | ISO dates or datetimes (UTC) |
| `sort` | `{by, direction}`; `by` is `title`, `created_at`, `updated_at`, `published_at` or a field key (numeric when the values are number-like; empty values last) |
| `group_by` | a field key, `publish_status` or `entry_type`: counts per value over the whole match |
| `limit`, `offset` | page size (default 10, max 200) and offset |

In `where`, `sort` and `group_by` a bare key is always the type's own field (a type may have its own `status` field); use `publish_status` for the entry's lifecycle status. `include_fields` / `include_metadata` put those values on each row. The result has `count` (the true total), `returned`, the rows and `groups`; `where`, field sorts and `group_by` read at most 5,000 candidate rows, and the result says so when that bound is hit.

**Linking to entries.** Marvin only knows where your site shows an entry if you tell it: set the workspace's **Canonical URL** (Settings → General) and a **Page URL pattern** on the entry type (see [Publishing API → Entry page URLs](publishing-api.md#entry-page-urls)). Then `find_entries`, `get_entry`, `get_collection_entries` and `search_content` give each entry of that type a `url`: absolute when the Canonical URL is set, otherwise the site path. Agents are told to link entries with that `url` exactly, to prefer the absolute form in anything that may be emailed, and never to write placeholder links such as `[Title](#)`; an entry without a `url` is written as plain text and the reply says it couldn't be linked. An unpublished entry still gets its `url` (where it will live), and its `status` says it isn't live yet. `compose_entry` and `revise_entry` follow the same rule: put the `url`s in the brief, or the entries are named without links. Nothing changes for a workspace that sets neither.

**Ask.** The Ask page is the agent chat. A run with `thread_id: "new"` opens a server-side thread; passing an id continues it and its stored turns become the history. Threads are yours only (admins see every thread in the workspace); you can reopen, rename and delete them. The **Threads** panel lists all of them across agents, newest activity first, each labelled with its agent (the main agent under the assistant name), so a conversation started in the bubble shows up there too; a hand-off's specialist thread is indented under the thread that made it. **This agent only** narrows the list to the agent picked above (remembered per tab); for a specialist that includes its hand-off threads, each noted "from a hand-off in …" with the parent thread's title. Runs return `threadId` and `sources` (citations extracted from the run's own `search_content` results). If the client mints a `client_run_id`, it can poll live `thinking` / `tool_call` / `tool_result` events while the POST is in flight; the page shows them as a step timeline. Files you attach (up to four: images, text, Markdown, CSV, JSON, PDF, Word) are uploaded as **Ask files** and sent as the run's `attachments`, separate from what the page is showing; they stay with the conversation for every later turn until you remove them. The run checks each is an asset of this workspace and not in the Trash (otherwise 422), lists them for the model by name, type and size, and keeps them on your turn of the thread.

Two read-only tools support this: `workspace_overview` (entries by type and status, collections, assets, resources, tags, embedding-index coverage, and a `structure` listing every workflow, scheduled task, incoming and outgoing webhook, MCP server, integration and agent by name and slug; below ADMIN it lists the agents only) `view_image(asset, question?)`, which asks the vision model about an image and writes nothing back to the asset (only a `tool:view_image` execution row for cost accounting), and `read_attachment(asset, max_chars?)`, which returns the text of a document asset (plain text, Markdown, CSV, JSON, PDF or Word .docx; at most 20,000 characters, saying when it cut; a scanned PDF has no text to return) and writes nothing. `run_workflow` matches a workflow by slug, name or id, case-insensitively, and lists the workflows that exist when nothing matches.

**Media players.** `add_embed(entry, url, field?, after_heading?)` puts a YouTube, Vimeo, Spotify, SoundCloud, Apple Music, Apple Podcasts, TIDAL, Simplecast or Transistor player (or Bandcamp's, from its embed code) into an existing entry. It needs EDITOR and sits in the `entries_author` row. It always stages the change as the entry's pending suggestion, so nothing goes live until someone applies it. In a markdown field the link goes in as its own paragraph, under `after_heading` or at the end; in an `embed` field it becomes the value. It is idempotent: a link already there comes back as `already_present`. `preview_embed(url)` (AUTHOR, `entries_read`) says whether a link becomes a player and what it is. `compose_entry` and `revise_entry` are told to put a media link alone on its own line for a player and never to invent one. See [Media embeds](media-embeds.md).

**Marvin's manual.** `search_docs(query, limit?)` searches this manual and returns the best-matching sections with their page, heading, anchor, a snippet and the published link; `read_doc(path, section?)` returns a page, or one section by anchor or heading, as markdown. They read the manual bundled with the running version (not the published site, which can be a deploy ahead or behind), rank by keywords with heading and title boosts (no AI cost), and say so plainly when the manual is not bundled. Both are in the **Read Marvin's documentation** row (`docs_read`), allowed by default for every agent including Ask. When they are bound, the preamble tells the agent to answer how-to questions about Marvin from the manual, cite the page's link and use its exact screen labels instead of guessing.

**The bubble.** The Ask bubble in the admin wears the workspace persona: the **Assistant name** and **Bubble icon** from AI Settings (an emoji, or an image URL that wins over the emoji; blank means "Marvin" and 🤖). Its agent conversations are server threads, one per agent (the default agent, or one picked with `/use`), so they appear under **Threads** on the Ask page and the server, not the browser, holds the agent's memory. A run keeps going if you navigate away: the next page shows the thinking placeholder and picks the answer up from the thread, and stops waiting after 10 minutes with a link to the conversation. **Clear** starts a new thread. When an Ask-first tool parks the run, the bubble shows the approval card in the conversation — one checkbox per call, **via** chips for a specialist's asks, **Approve selected** and **Deny all** — and the answer (or the next card) arrives as its reply. This works with the Ask page switched off (the decision is sent with source `bubble`); with the Ask page on, the card also links to the conversation there (`/workspace/settings/ai-ask?thread=<id>`). `/tools` marks the tools that ask first. The other bubble commands (`/ask`, `/chat`, `/tools`, `/agents`, `/use`, `/help`) do not use a thread. The bubble keeps its threads, a run in flight, the agent picked with `/use` and the transcript per workspace (in the tab's session storage), so a tab that switches workspaces never sends one workspace's thread to the other. If a remembered thread is gone (deleted on the Ask page, so the server answers 404), the bubble forgets it and sends the message again on a new thread. **Attach and speak.** 📎 next to the input attaches files (images, text, Markdown, CSV, JSON, PDF, Word), up to four per conversation; you can also paste an image into the input or drop files on the panel. Each is uploaded as an Ask file (slug `ask-…`, metadata `attachedVia: bubble`; see **Ask files** below) and shows as a chip above the input; the files go with every message to the agent until you remove them (×) or **Clear** the conversation, separately from the page the bubble is looking at, and your message names them the first time they go. Uploading takes the Author role, so 📎, paste and drop are not offered to a Viewer. 🎙 **Speak** types what you say into the input with the browser's own speech recognition (Chrome, Edge and Safari; no button on Firefox). It keeps listening through pauses until you press ■ (or after 20 seconds of silence), and nothing is sent until you press Enter or ➤. The input grows with what you type; Enter sends and Shift+Enter starts a new line. Offline, ➤, 📎 and 🎙 are disabled under a note, and the draft and chips are kept. The Ask page attaches and listens the same way, and reopening a thread there brings back the files its last question carried. The bubble rests at the bottom-left of the window. Drag it anywhere: it remembers the spot in this browser as distances from the nearest edges, and stays on screen when the window is resized or a phone rotates. Double-click it to send it back to the corner.

**Ask files.** A file attached to a question (bubble or Ask page) is an Ask file, not a library asset: the asset's `scope` is `ask` (`library` for everything else). It is uploaded so the agent can open it, and stays out of everything that works on the library: the Assets page and its count, `GET /api/platform/assets` (which lists Ask files only with `scope=ask`), workspace statistics and tag counts, the AI's asset queries (`list_assets`, `attach_tag`'s filter, the Trash's `match`, workflow asset targets — so "trash every unattached image" spares them), `workspace_overview`, smart collections, the search index, the publishing API (never served to a site) and the orphaned-assets task. Uploading one fires no `asset_uploaded`. **Assets → Ask files** (`/workspace/assets/ask-files`) lists them, newest first, with **Move to Assets** (AUTHOR and above, `POST /api/platform/assets/{id}/move-to-library`) and **Move to Trash** (EDITOR). The agent's `move_to_assets(assets, name?)` does the same (category **Assets: import**, EDITOR; `name` renames a single file), and attaching an Ask file to an entry (`attach_asset`, the entry editor, an entry's `asset_ids`) moves it first, so a site never links a file it can't serve. A move fires `asset_uploaded`, so workflows and webhooks see it as a new library asset. Deleting a thread moves the Ask files its questions carried to the Trash (restorable), except those another thread still carries; library assets are never touched. Files attached before this existed (slug `ask-<name>-<time>` or marked `attachedVia`) became Ask files on upgrade, unless an entry already used them.

**Bubble lines.** Between answers the bubble speaks canned lines: a greeting when the panel opens, a tagline rotating under its name, a line while it works, an opener for an error, and emotes such as *smiles*. Under AI Settings → **Persona**, **Bubble lines** holds the workspace's own set, one list per kind, one line per row. When you save a **Character** (a new or changed one, a new assistant name, or any Character while there are no lines yet), one AI call writes the lines in that character's voice; it runs in the background, so the save returns at once and the card says *Writing lines from the persona…* until they arrive. The call uses the workspace's provider and model, counts against **Usage & Limits** like any other run, and appears under **AI Executions** as `generate-bubble-lines` (trigger `settings`). If it is refused (a limit is reached, AI is off) or the model's answer is unusable, the previous lines stay and the card says why. Editing the lists and clicking **Save lines** (or **Save Settings**) marks them *Edited*: a later Character change leaves edited lines alone, and only **Regenerate from persona** replaces them (it asks first). **Clear** goes back to the built-in lines; so does clearing the Character, for lines that were generated. An empty list falls back on its own, to the lines shown greyed in its box. Which lines the bubble speaks, per list: the workspace's own; otherwise Marvin's while the assistant is named Marvin, whatever its Character; otherwise, for a renamed assistant, a plain neutral set — a renamed assistant never speaks Marvin's lines.

**Bubble character.** Under AI Settings → **Persona**, **Bubble character** replaces the round icon with an animated character, one animation per state. The picker is a row of cards, one of which is outlined as the current choice: **None — the icon**, one card per pack in the platform's character library (below) showing the pack's idle animation, and **Own upload**, which shows your idle animation once there is one. Keyboards and screen readers get it as a plain radio group. For your own, click **Upload character…** and choose a .zip or GIF, WebP or PNG files. Files are recognised by their content, never their extension, and SVG is never accepted; one upload holds at most 20 images, 5 MB each and 20 MB in all, and other files are skipped and listed. An image with an opaque solid background (a box around the character, common in generated packs) has the background connected to its edges made transparent, and the picker lists the files it changed; the rest of the image is kept exactly. Files stored before uploads did this can be cleaned in place by an operator (see [Operations → Storage](../operations.md#storage)). Each file's name (without extension, case ignored, `_` and spaces read as `-`) picks its state:

| State | Label in the picker | File names, best first | Plays when |
|---|---|---|---|
| `idle` | Idle | `idle` | nothing else is happening; required |
| `idle_variant` | Idle fidget | `look-loop`, `look`, `look-around` | once now and then while idle, 20–40 seconds apart |
| `greeting` | Greeting | `waving`, `wave`, `greeting` | the panel opens |
| `thinking` | Thinking | `review`, `thinking`, `think` | a message is sent, before the agent's first step |
| `working` | Working | `running`, `working`, `run` | the agent's steps are running |
| `waiting` | Waiting for approval | `waiting`, `wait` | the run is parked on an Ask-first approval |
| `success` | Success | `jumping`, `jump`, `success`, `idle-jump-idle` | the answer arrives |
| `error` | Error | `failed`, `error`, `fail` | the run fails |
| `move_left`, `move_right` | Dragging left, Dragging right | `running-left`, `move-left`, `walk-left`; `running-right`, `move-right`, `walk-right` | the bubble is dragged that way |

Greeting and success play for about two seconds and error for four, then the character goes back to idle; the newest event always wins. When two files claim one state, the one matching the earlier name wins. Files named anything else are kept, unassigned: each state's row has a dropdown of every file in the pack, so any file can play any state, and the picker lists the files no state uses. With no file named for idle, the first image plays as Idle until you pick another. Idle can be changed but not cleared. A state with no animation of its own falls back to Idle (dragging tries Working first); the row's thumbnail is dimmed and its dropdown reads "— default (falls back to …)". Changes save as you make them, with no **Save** needed. The images are stored as workspace assets; replacing the character, switching to a library pack or to **None** (after a confirmation) deletes exactly the assets it created. Viewers who prefer reduced motion see a still of each state's image and no fidget or drag motion. If an image will not load (its asset was deleted, say), the bubble shows its icon instead.

**Agent characters.** On **Agents**, an agent's own character is under **Edit → Bubble character**, below Icon and Name; the **Character** button on its card opens the same picker without opening Edit. The cards there are **None — the workspace's character**, each library pack and **Own upload**. A new agent gets a character once it exists (the **New agent** form says where to find it). The bubble shows the character of whoever is talking: after `/use <agent>` that agent's, until `/use marvin`, and during a hand-off the delegate's while it works, until the answer lands. An agent's character covers what it covers: a state it lacks plays the workspace's, and with no character on either the bubble shows its icon. Built-in agents have no character of their own; they show the workspace's.

**Character library.** A platform super admin installs packs once, under **Admin → Extensions → Character Library** (`/admin/character-library`), and any workspace or agent can pick one. **Add a pack** takes a name (blank uses the .zip's name) and the same kind of upload. Each pack has a card where you can **Rename** it (its slug stays), give it new files with **Replace files…**, pick its states, or **Delete** it. Everyone using a pack gets its new files, name and picks. A workspace cannot change a library pack's animations; it uploads its own instead. The card says who uses the pack. **Delete** on an unused pack asks to confirm. On a pack in use it names the users and asks whether to delete it anyway: if you confirm, they are unlinked first (a workspace falls back to its icon, an agent to the workspace's character), then the pack and its files are removed. A pack's files belong to no workspace (see [Operations → Storage](../operations.md#storage)).

**External MCP servers.** Register HTTP (streamable) or SSE servers (stdio is not supported) with an optional **Auth secret** (a workspace secret slug sent as a Bearer token). Servers start disabled and expose nothing until you allow tools (deny by default). **Choose tools** runs `tools/list` and returns each tool's `readOnlyHint` / `destructiveHint`; bound tools are named `mcp__<server>__<tool>` and sorted into the `mcp_read`, `mcp` (writes, or no hints) or `mcp_destructive` rows from those hints, so a read-only agent can reach a server's read tools. The **External MCP tools** master switch on the MCP Servers page (`external_mcp_enabled`) must be on. A tool call waits up to `MCP_TOOL_TIMEOUT_SECONDS` (default 45) before the model is told it failed, and a result longer than `MCP_TOOL_RESULT_MAX_CHARS` (default 20,000) is cut, with a note asking the model to narrow the call.

**Search index.** `search_content` and grounded Ask answers read an embedding index of the workspace's published entries, resources and assets (icons and logos with nothing but a name and tags are left out). Publishing or editing a published entry indexes it, and unpublishing, archiving or deleting it takes it out, so drafts, inbox and archived entries are never searchable. A save that leaves the indexed text unchanged (a workflow writing metadata, say) does not re-embed. **Reindex now** on the Ask page rebuilds the whole index in the background, so you can leave the page: chunks are embedded in batches, unchanged items are skipped, and drafts and archived entries left over in the index are purged. The card shows chunks held, items indexed out of indexable items, the run's progress and the last run's summary; while a run is going the button is disabled and a second request gets 409. The finished run emits `ai_embeddings_reindexed` with indexed, skipped and failed counts and the first error, which shows as a **Search index** activity toast. The `ai_reindex_embeddings` scheduled task uses the same path. Reindexing needs EDITOR or higher and a provider with embeddings.

## How to use

1. On **AI Settings**, turn on **AI Features**, choose a **Credential Mode** (Platform or Workspace), a provider and model, an **Approval Mode**, and the **Invocation Sources** you want. Under **Persona**, optionally set the assistant name, bubble icon, bubble character and **Character** (**Preview** shows it with the default tone); under **Tones**, the default tone and any tones of your own. Under **Usage & Limits**, optionally set a monthly cost limit, a daily request limit and an output-token cap.
2. On **MCP Servers**, turn on **External MCP tools** and add servers if agents should use them.
3. On **Agents**, click **+ New agent**: icon, name, slug, description, "Hand off when…", instructions, suggested prompts, model, kind, default tone, "Who may talk to it", **Allow writes**, **Enabled**. Adjust the Tools matrix per group or per tool (Inherit, Allow, Ask first, Block). New agents are read-only until you turn on Allow writes, and a write still needs the caller to be EDITOR or higher. Click **Character** on an agent's card to give it a bubble character of its own. **Edit → Preview prompt** shows what the agent will be sent, unsaved changes included; the New agent form has **Preview prompt** too, before the agent is saved.
4. On **Ask**, pick the agent, type or speak a question, optionally attach a file. Open **Threads** to reopen an earlier conversation, from any agent or the bubble; **Tools** shows the effective matrix for you. Approve or deny any "Before I continue, approve these actions" card.
5. Review usage on **AI Executions** (status, tokens, estimated cost per execution). Agent runs show as `agent:<name>` with the agent's current name, so renaming the assistant renames its history; hovering shows the stored `agent:<slug>`, which is what filters match. A model with no known price shows its cost as unknown (—) rather than Free; self-hosted providers cost nothing. The month at a glance is on **AI Settings → Usage & Limits**.

### Tones

Two settings shape how the assistant writes, and they do different jobs:

- **Persona** (AI Settings → Persona → **Character**) is *who your assistant is* and how it speaks. It is sent to the model labelled `Character:`.
- A **tone** is *how it delivers* a given run: instructions, plus a rule for how far the character reaches. It is sent labelled `Tone (<name>):`.

When both apply, one line settles any conflict: *"Where the tone and the character disagree on formality, length or mood, follow the tone; keep the character's identity and way of speaking otherwise."* So a gloomy character under a "Board report" tone stays recognisably itself but keeps it short and formal.

The **Tones** card on AI Settings lists the built-ins — **Auto** (character for chat, plain for work), **Professional** (plain everywhere, no character) and **Playful** (the character applies to everything) — and the workspace's own. Pick the **default** with the radio button; untick **Show** to leave a tone out of the pickers (the default can't be hidden; a hidden tone still works for agents and parked runs that already use it). Built-ins can be hidden but not edited or deleted. Changes save as you make them; only workspace admins and owners can change tones, while anyone may pick one per request.

**Add tone** takes a **Name** (1–60 characters, unique, not a built-in's), an optional **Description** shown in the pickers, **Instructions** (1–1500 characters of free text) and what to do with **your Persona's character**:

| Persona rule | Effect |
|---|---|
| Frame only | the character talks (greetings, framing, asides); work product follows the tone's instructions |
| Everywhere | the character applies to everything, work product included, alongside the tone — the tone still wins on formality, length and mood |
| Drop the character | no character for the run, just the tone — the safest choice for client-facing copy, since weaker models blur "everywhere" |

**Preview** on a tone's row (built-ins too) and **Preview prompt** in its form show what the tone adds to the system prompt with this workspace's character, in parts: a plain-words line for the persona rule (for example *Frame only: the character talks, work product follows this tone*), **From your Persona** (the `Character:` block, with a link to the Persona card — or why there is none: the tone drops it, or no Character is set), **From this tone** (how far the character reaches, and the instructions), **Which wins** (the line above, when both apply), the **Full prompt text** exactly as sent, and a rough token count — it is sent with every agent step. A workspace can have up to 20 tones. A tone's slug is made from its name when it is created and never changes, so renaming a tone keeps every agent and default that points at it. A tone that agents default to can't be deleted: the save fails (409) naming the agents — pick another default tone for them first. Deleting the default tone needs a new default.

**Where a tone applies.** For a run, the first that names a tone wins: the request's tone (the Ask page's **Tone**, the bubble's `/tone`, an action such as "Review & suggest"; for a named agent a request's `auto` doesn't count), then the agent's default tone, then the workspace default, then Auto. A slug that names no tone (deleted since, or imported) is skipped with a warning in the log rather than failing the run. Hand-offs carry an explicit tone to the specialist. Plain chat (`POST /chat`) uses the request's tone or the workspace default, like Marvin. Compose and revise drafts use the tone too, but an entry type's own **Voice** wins (the entry type's **Recipe → Voice**, "Overrides the tone for AI drafts of this type"; stored as the recipe's `enrichment.voice` and sent as `Voice:`); with no Voice the draft gets the tone's instructions (and the character under an *Everywhere* tone, with the same precedence line; Auto and Professional leave drafts plain, Playful writes them in the character). The agents' `compose_entry` / `revise_entry` tools use the run's tone.

**The bubble.** `/tone` lists the tones; `/tone <name or slug>` sets one for the rest of the browser session and shows it as a **Tone** chip above the conversation (× clears it); `/tone default` goes back to the workspace's.

**Previews where you set things.** The same labelled parts show up wherever a part of the prompt is set:

- **Persona → Character → Preview** shows the character with the workspace default tone — the exact section the AI receives — from the form as it stands, so an unsaved Character or assistant name previews too (a blank Character previews Marvin's default one while the assistant is named Marvin). While open it follows your typing.
- **Agents → Edit → Preview prompt** (built-ins: **Preview prompt** on their card) shows everything an agent's system prompt holds, in prompt order and built by the same code as a run: **Workspace context** (the preamble, folded), **From this agent** (its instructions, or **Default instructions** when it has none), **From your Persona**, **From the tone …** (the agent's default tone, else the workspace default), **Which wins**, and **Other agents** it can hand off to or suggest (folded). A line counts the tools it gets as you would run it from Ask, per matrix row and how many ask first; their definitions are sent too but not shown. The **Full prompt text** and a token estimate close it. Unsaved form values are used; what the user is looking at and the conversation are added at run time. Nothing calls a model.

| Method and path (`/api/groups/ai-settings`) | Purpose |
|---|---|
| `GET /tones` | any member: every tone (built-ins first) with `builtin`, `hidden`, `usedBy` (agent slugs), plus `defaultTone` and the limits |
| `PUT /tones` | ADMIN+: `{tones: [{slug?, name, instructions, persona: frame\|everywhere\|drop, description?}], hidden: [slug], defaultTone?}` replaces the custom tones and hidden list; 422 for an invalid list, 409 (`detail.tones: {slug: [agents]}`) when a removed tone is still an agent's default |
| `POST /tones/preview` | ADMIN+: `{slug}`, a draft `{name, instructions, persona}`, or neither for the workspace default; optional `personaPrompt` / `assistantName` stand in for the stored ones (unsaved Character fields) → `{clause, tokens, persona, personaSummary, hasPersona, character, fromTone, rule, toneSlug, toneName}`: the whole section (`clause`) and its parts — `character` from the Persona, `fromTone` from the tone, `rule` the precedence line (each `""` when it doesn't apply) |

Workspace export and import carry `tones` and `hiddenTones` with the AI settings; an import re-validates them and, if they don't validate, keeps the built-ins only.

### Usage and limits

The **Usage & Limits** card on AI Settings shows this month's estimated spend against **Monthly cost limit (USD)**, today's runs against **Max requests per day** (with a meter each, and the date the month resets), and a **Top this month** table of the operations and agents that cost the most (runs, tokens, estimated cost). **Max output tokens per request** caps each model call; blank uses the app default (`AI_DEFAULT_MAX_TOKENS`). A blank limit means no limit.

| Limit | Measured | At the limit |
|---|---|---|
| `max_cost_per_month_usd` | estimated cost of completed runs since the 1st of the month (UTC) | new AI runs are refused (429) until the month resets |
| `max_requests_per_day` | runs started since midnight UTC, failed ones included | new AI runs are refused (429) until midnight UTC |
| `max_tokens_per_request` | output tokens per model call | the call is capped, not refused |

The request and cost limits are checked before operations, compose, revise, agent and chat runs (Ask, the bubble, hand-offs, resuming a parked run) and workflow AI-operation steps; a step over a limit fails with the reason. Crossing `AI_BUDGET_WARNING_PERCENT` of the monthly limit (default 80; 0 turns the warning off) fires `ai_budget_threshold_reached`, reaching it fires `ai_budget_exceeded`, and a provider call refused for lack of credit fires `ai_provider_quota_exceeded`; each shows as an activity toast that stays until dismissed. Costs are estimates from Marvin's price table, embedding calls for the search index are not counted, and the provider account's own balance is not visible to Marvin.

`GET /api/groups/ai-settings/usage` returns the same numbers: `limits`, `warning_percent`, `level` (`ok`, `warn`, `over`), `month_cost_usd`, `month_tokens`, `month_runs`, `month_percent`, `today_runs`, `day_percent`, `resets_on` and `by_operation` (up to 8 rows with `operation`, `label`, `runs`, `tokens`, `cost_usd`).

### OpenAI and other providers

The official OpenAI API is called through OpenAI's Responses API for chat, tool calls and structured output, so any chat model takes the same length limit and can call tools while it reasons. An OpenAI-compatible server (the OpenAI provider with a custom base URL) and Azure OpenAI use Chat Completions. No provider sends a temperature unless `AI_DEFAULT_TEMPERATURE` is set, so each model uses its own default. If a server still refuses a parameter (a configured temperature, `max_tokens` where it wants `max_completion_tokens`, tools while reasoning), Marvin retries with the fix named in the 400 and remembers it for that model until the process restarts. The OpenAI model picker leaves out models that cannot chat (embeddings, speech, image, moderation and similar).

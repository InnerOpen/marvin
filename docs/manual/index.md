# Marvin

Marvin is a headless CMS. Every workspace has its own content model, automation, AI setup and API credentials; the admin UI, the platform API under `/api/platform/…` and the publishing API under `/api/publish/{workspace_slug}/…` are all scoped to one workspace at a time. This site is the manual for version 1.0.0-rc.197.

## What a workspace contains

| Area | What it is |
|---|---|
| Entry types and entries | You define entry types (field schemas); entries are the content. Each entry has one status: `inbox`, `processing`, `draft`, `needs_review`, `approved`, `published`, `archived`. New entries start in `inbox`. A YouTube, Vimeo, Spotify, SoundCloud, Apple, TIDAL or podcast link on its own line, or in a **Media embed** field, becomes a player on the site ([Media embeds](whats-new/media-embeds.md)). |
| Collections | Manual lists of entries, or smart collections whose membership follows rules (entry types, statuses, field conditions, rolling `published_within_days` / `created_within_days` windows), built visually and previewed with **Run Query**. **Visible to sites** decides whether the publishing API serves a collection. |
| Assets and resources | Uploaded files (local disk or S3) and external links, attachable to entries and served through the publishing API. |
| Forms | A submittable entry type is a form. A public submit creates an `inbox` entry and emits `form_submission_received`, guarded by rate limits, honeypot, CAPTCHA and submission protection. |
| Publishing API | Read-only endpoints for sites (`entries`, `collections`, `assets`, `resources`, `entry-types`, `site`), authenticated with an API client token. |
| Automation | Events and the event log, workflows (triggers, conditions, steps), incoming webhooks, outgoing webhooks and scheduled tasks. |
| Integrations and blueprints | Provider plugins with connections, actions and event subscriptions, plus blueprints that create the entry types, fields, collections, scheduled tasks, incoming webhooks, workflows and event subscriptions they need. |
| AI | Operations (summaries, tags, alt text, …), agents with a per-tool permission matrix, Ask threads, the Ask bubble with an optional animated character, a search index of published content, usage limits, and external MCP servers. |
| Admin | Platform overview, users, workspaces, installed plugins, backups, maintenance, submission protection defaults, the bubble-character library, system scheduled tasks. |

The admin sidebar shows **Dashboard**, **Ask**, **Content** (**Entries**, **Collections**, **Assets**, **Resources**), **Workspace → Settings** and **Profile**; super admins also get **Administration → Admin Settings**, which opens the platform admin at `/admin`. Its **Overview** has a card each for version and health, people, plugins, the last backup (flagged when there is none or it is older than 7 days), platform events (how many in the last 7 days, and the latest) and scheduled tasks. Its sidebar groups the pages as **People & access** (Users, Workspaces, Roles), **Settings** (Site Settings, Email, Submission Protection), **Extensions** (Plugins, Character Library) and **Operations** (System, Events, Scheduled Tasks, Backups, Maintenance), and ends with **Back to workspace**. This manual names those pages **Admin → group → page**, for example **Admin → Operations → Scheduled Tasks**. The **Entries** row carries a badge with the number of entries waiting in `inbox`. The top bar holds the activity bell, **Review Queue** (entries in `needs_review` or `approved`) and **Logout**. The dashboard's **Needs Attention** panel counts entries in the inbox (form submissions, AI drafts) and drafts awaiting review separately, each linking to its own entries filter, plus pending AI suggestions and failed runs from the last 7 days.

**Where you are.** Every platform admin, workspace settings, automation and publishing page shows the pages above it as a trail over its title, each one a link back up: **Admin › Users** over a user's name, **Settings › Email** over **SMTP Configuration**, **Settings › Events › Entry published** over the page that connects a webhook to that event. There are two starting points: **Admin** (`/admin`) for platform admin pages, and **Settings** (`/workspace/settings`) for everything listed on the workspace Settings page, including workflows, events, webhooks, scheduled tasks, the Event Log, the site and API clients. Below 640 px only the page one up shows, as **‹ Email**. Pages at the top (the admin Overview, Settings, the workspace dashboard) have no trail. Content pages (entries, collections, assets, resources) keep their own headings for now.

**On a phone.** At 920 px wide and below, the sidebar of the workspace admin and of the platform admin becomes a drawer behind a menu button (three lines, "Open navigation") in the top bar. It closes on the backdrop, Escape, a link, or widening the window, and keeps keyboard focus inside while open. On a phone the top bar's actions wrap under the title, pages do not scroll sideways (wide tables scroll inside their own box), the entry editor shows the form first and Entry Details after it, activity toasts stay inside the screen edges, and the Ask bubble rests bottom-left. Desktop layouts are unchanged.

**Activity toasts.** While the tab is visible, the admin polls `GET /api/platform/events/feed?since=` every few seconds and shows a toast for workflow runs and failures, incoming webhooks, site rebuilds queued and sent (with an "N changes" list of what each covers), failed webhook deliveries, site builds and deploys (started, completed, failed), failed scheduled tasks and AI operations, scheduled publishes that are waiting (the entry can't publish yet, or needs approval), AI budget warnings and limits, full search-index reindex runs, form submissions, and entries created, updated, published, unpublished or deleted by someone else. Failure and warning toasts stay until dismissed; the rest fade, but not while the pointer or focus is on them or a change list is open. Click the bell to cycle **Activity: all** → **Activity: failures only** (failures and warnings) → **Activity: off**; the choice is remembered per browser and changes nothing on the server. Two toasts update in place. A queued site rebuild shows "Site rebuild queued — building in about …" and becomes **Site rebuild sent** when it goes out; a workflow run shows "Workflow '…' is running…" (with the number of entries for a query run) and becomes its result when it finishes. A run that finishes before the next poll shows only its result. Workflow and failed scheduled-task toasts link to that workflow or task. Everything shown is already in the event log.

**Event log.** **Automation → Event Log** lists the newest 100 events. Each row names what its event is about (`entity_type` and `entity_id`) and links it to its admin page where there is one: an entry, asset, collection, resource, entry type, scheduled task, workflow, outgoing webhook, and the list pages for incoming webhooks, integrations, members, invitations and API clients. Other types show as plain text. A workflow run also names what triggered it, for example "from Entry 'Issue 12'". The entity chips filter the list by type, and the dashboard's activity list links each entity the same way. Site rebuild and deploy events (`site_rebuild_queued`, `webhook_triggered`, `site_deployment_*`) are about the workspace's deploy target: the one outgoing webhook, or integration action, wired to `webhook_triggered`. When there are several, these events name none. A deployment id reported by the host stays in the event's data.

**What the log records.** Each event type has a default in the event catalog: three busy internal ones (`scheduled_task_triggered`, `scheduled_task_started`, `webhook_task`) are off and everything else is on. The **Audit coverage** panel at the top of the Event Log says how many types are left out. A workspace OWNER or ADMIN gets a switch per event type there, grouped by category, with a filter box; a type changed from its default shows **Reset to default**. Other members see the list of types left out. A type switched off is not written to the log, so it can't be found there later. Its webhooks, workflows and notifications still fire, but the things that read the log lose it too: activity toasts, the dashboard's activity list, workflow dry-run samples, and the last rebuild and build shown by `GET /api/platform/site/rebuild`. Security events are locked and always recorded: members and invitations, API clients and their tokens, secrets, workspace settings, and AI approvals. So is any event type the catalog doesn't list. Platform events (below) aren't workspace settings at all, so the panel doesn't list them. Each change is itself recorded as `workspace_settings_changed`, for example "Audit settings changed: entry_updated off". Through the API, `GET /api/groups/audit-settings` (OWNER/ADMIN) lists every workspace catalog type that something sends with `default_audited`, `audited` and `locked`. `PATCH` the same path with `{"overrides": {"entry_updated": false}}` to change types. `null` puts a type back to its default, an unknown or platform type gets a 422 and a locked one a 409. `GET /api/groups/audit-settings/excluded` (any member) lists the types left out. A change applies at once on the server that saved it and within 30 seconds on any other server process.

**Events.** **Automation → Events** (`/automation/events`, workspace OWNER/ADMIN) lists every workspace event type; platform events (below) aren't listed, and their pages send you back to the list. A filled dot means something in the workspace reacts to it (a workflow, integration action, email or webhook, however it was connected); a ring means everything that reacts is switched off. Hovering a row counts both directions: how many things send it, how many react (and how many of those are off), Marvin's built-in reactions and when it last happened. Opening a type shows its whole story in three parts. **Sent by**: Marvin's own code (for example "Publishing an entry (app, API, CLI)"), the workflows whose steps send it (Emit event, Request Site Rebuild, an entry step), the incoming webhooks that start those workflows, and the scheduled tasks that send it. **What happens**: everything that runs when it fires, grouped by kind, each with an On/Off badge. Emails, webhooks and integration actions you connected here keep their **Edit** and **Disconnect** buttons. Workflows, and anything an integration installed (marked **Installed by <integration>**), are read-only here with an **Open** link to where they are managed, so the event page never fights the integration that owns them. Built-in reactions (site rebuild, AI search, media embeds, smart collections) are listed last, muted. For an invitation, the system email row says whether Marvin's own email sends: it does unless the workspace connects its own template of that type. **Recent**: the newest events of the type, each opening its row in the Event Log; when Audit coverage leaves the type out, the page says so and links there instead. **Caused by** and **Leads to** link the events in its chain (for example Entry Published → Site Rebuild Queued → Site Rebuild Sent). **Subscribe** opens the menu of what can still be connected: **+ New workflow on this event** (shown when a workflow can trigger on the type) opens the workflow builder with that event as the trigger (`/automation/workflows?trigger=<type>`), and the webhook, email and integration-action options connect as before. The **Workflows** page marks each workflow an integration's blueprint created with **Installed by <integration>**. The routes behind it are `GET /api/platform/event-types/connections` (one row per shown workspace type, with its catalog `name` and `category`) and `GET /api/platform/event-types/{type}/connections` (OWNER/ADMIN). **Site Rebuild Sent** (`webhook_triggered`, under Publishing) is the signal deploy hooks listen to: connect your host's deploy hook (an outgoing webhook, or an integration action such as Cloudflare Pages → Deploy) to it. Outgoing webhooks announce themselves: **Webhook Created**, **Updated** and **Deleted** carry the webhook's name, type, switch and subscribed events (never its URL or headers), and **Webhook Delivery Failed** is sent once for each delivery that still failed after its retries, with the webhook, the event it carried and the HTTP status or kind of error (never the URL, headers or a body; a webhook on that event failing doesn't announce itself again). Event types nothing sends are hidden everywhere (this list, the pickers, Audit coverage, the admin Events filter): `webhook_delivery_succeeded` (the webhook's activity log already records each delivery), `site_published`, the security signals above, and a few declared but never built. `site_build_started`, `_completed` and `_failed` are old names for the `site_deployment_*` events: a workflow trigger, Emit event step or subscription that names one is saved and run as its `site_deployment_*` counterpart.

**Platform events.** Some events belong to the platform rather than to a workspace: accounts (`user_signup`, `user_updated`, `user_deleted`, `user_password_reset_requested`, `user_password_reset_completed`, `token_refreshed`), workspaces as a platform admin creates, edits and deletes them or a user switches to them (`workspace_created`, `workspace_updated`, `workspace_deleted`, `workspace_activated`), personal API tokens (`api_token_created`, `api_token_rotated` and `api_token_revoked`, sent when you create, rotate, revoke or delete one of your tokens: its name and owner, never the token), the platform's security signals (`api_rate_limit_exceeded`, `login_failed_multiple_times`, `suspicious_activity_detected`; hidden until a feature sends them) and platform backups (`backup_*`). The event catalog marks them `scope: "platform"`, and the workspace side doesn't offer them: they're left out of `GET /api/event/types`, so the Events list and the webhook, email and integration pickers don't show them, and no workflow can trigger on one. Marvin's own welcome and password-reset emails still send on them; those aren't subscriptions. They are still stored with the workspace they were dispatched with (a new user's workspace, the workspace created or switched to) and still fire any webhook or notification already connected to them in that workspace, but nothing a workspace reads shows them: not the Event Log or its filters, a single event (`GET /api/platform/events/{event_id}` answers 404), entity and user history, activity toasts, the dashboard's activity list, workflow dry-run samples, or the agent's `list_events` and `get_entity_history` tools. They are always recorded. Super admins read them on **Admin → Operations → Events** (`/admin/events`): a log across every workspace, newest first, 50 to a page, with the event, its workspace, the user it is about (who acted, or for a sign-up the new account) and its message, and the full payload on expanding a row. Filter by event type, workspace and a from/to day; days and times there are UTC. Filtering by one type (or clicking a row's type) also shows what sends it, its built-in reactions and system email, and each workspace's own reactions to it, grouped by workspace (`GET /api/admin/event-types/{type}/connections`). On a phone each event is a card. Through the API (super admin only; anyone else gets a 403): `GET /api/admin/events` with `event_type`, `workspace_id`, `start_date`, `end_date`, `page` and `per_page` (at most 100) returns `{page, per_page, total, total_pages, items}`, each item with `workspaceName`, `userName` and `userEmail`; `GET /api/admin/events/{event_id}` returns one with its `eventData` (404 for a workspace event); `GET /api/admin/events/catalog` lists the platform types. Before this change these events appeared in each workspace's Event Log.
